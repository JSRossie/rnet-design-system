This document describes the nightly backup job for the R—Net file store, how to verify it ran, and what to do when it didn't. It is the canonical reference — if a procedure here disagrees with memory, the document wins. Overview

The job runs at 03:15 local time and writes an incremental snapshot to the offsite target. A full snapshot is taken every Sunday. Average runtime is twelve minutes; anything past thirty minutes should be treated as a stall. See the escalation path below before paging anyone.

Note — the job holds a read lock on the file store for its first ~90 seconds. Schedule no other writes against NODE-04 in that window. A plain blockquote re-derives the system's note callout: bg-callout tint with an accent-warm border, matching .alert--note without the class.

What the job touches

  • The primary file store at /srv/store
  • The metadata index (rebuilt, not copied)
  • The offsite target — credentials in the vault, never on disk

Running a verification

After any snapshot you can confirm integrity in three steps. Run them in order; step two depends on step one having written the manifest.

  1. Pull the latest manifest from the offsite target.
  2. Compare the manifest checksum against the local ledger.
  3. Restore one sentinel file and diff it against source.

The whole check is scripted. From the node:

$ rnet-backup verify --node NODE-04 --since last
  ✓ manifest pulled        (offsite, 1.2 MB)
  ✓ checksum matches ledger
  ✓ sentinel restore       (delta: 0 bytes)
verification passed — snapshot 2026.05.14-0315 is sound

OK — a passing verification means the snapshot is restorable. Semantic callouts (ok / warn / alert) reuse the R/Y/G layer and stay separate from the brand accent.

Caution — if the sentinel restore reports a non-zero delta, the snapshot is intact but the source changed mid-run. Re-run after the write window closes.

Alert — a failed checksum means the offsite copy is corrupt. Do not delete the previous snapshot. Escalate immediately.
